# DB diagnostics hook measurement

2026-11-03, Apple M1, macOS 26.3.1. `cargo test --release --lib measure_hook_overhead -- --ignored --nocapture`: five sequential passes, each 50,000 cached indexed point reads against 10,000 in-memory rows. Each pass compares no trace hook with statement/profile/row tracing and statement counters; it excludes worker scheduling and slow backtrace capture. This microbenchmark is not an end-to-end workload.

Initial overheads: 19.97%, 19.49%, 26.67%, 29.51%, 30.24%; median 26.67%. After adding the exact-match fingerprint hook, the same benchmark measured 39.37%, 37.13%, 37.47%, 34.79%, 36.38%; median 37.13%. No variance or system-load control was applied.

After the PROFILE-only redesign (status sampled at 1 ms or above, no row callback, existing 1,000-step progress handler), the same release microbenchmark measured paired overheads of 8.59%, 8.01%, 7.37%, 9.53%, and 6.56%; median 8.01%. In the median-ratio pass, baseline was 10.569333 ms and the instrumented path was 11.416166 ms for 50,000 reads. This workload did not exercise slow-statement counter collection or backtrace capture. Other builds were active during the run.

The 37.13% figure is the median of five paired `(with_hooks / baseline - 1)` ratios, not an individual hook cost. Its median-ratio pass measured 10.575208 ms without hooks and 14.501500 ms with hooks for 50,000 reads.

The separate `measure_hook_components` release microbenchmark ran seven passes of the same cached point reads. Median times were 10.615541 ms baseline, 11.513125 ms for a PROFILE-only no-op callback, 11.886125 ms for PROFILE plus four non-resetting `sqlite3_stmt_status` reads at every completion, and 10.652209 ms for a 1,000-step progress callback reading the clock. Median paired baseline-relative changes were +8.90%, +12.12%, and -0.37% respectively; the latter is noise, not a speedup. The median paired incremental time for the four status reads over profile alone was 0.362084 ms per 50,000 reads. These component approximations are not additive, do not include the former STMT/ROW bookkeeping, and do not model slow captures or production workloads. Other builds were running concurrently; no load control was applied.

On the same machine, two production `cargo build --locked --release --bin shellboy` outputs measured 31,651,664 bytes without release debug information and 33,618,744 bytes with `CARGO_PROFILE_RELEASE_DEBUG=line-tables-only` (+1,967,080 bytes, 6.21%). The normal binary contains local Shellboy symbols under `nm`; a release-profile capture test passed, but it did not verify the filtered symbol names in a production event. The first build started while the branch was rebased, so these sizes are indicative, not a controlled same-revision comparison. No debug profile change is made on this evidence.

## Final-path comparison

On 2026-11-03, `cargo test --release --lib measure_final_hook_variants -- --ignored --nocapture` measured seven sequential passes on Apple M1/macOS 26.3.1. A 10,000-row in-memory table is read through cached statements, first 50,000 indexed point reads and then 100 reads of 1,000 rows. Each pass runs no hooks, PROFILE-only with production sampling, and production STMT+PROFILE+ROW plus the existing 1,000-step progress handler, in that order. There is no load control or randomization; other work may have run concurrently. Slow captures are not exercised; this is not an end-to-end throughput measurement.

Before caching repeated normalization, point-read median times were 10.705458 ms baseline, 11.874125 ms PROFILE-only, and 32.141166 ms production. Median paired overheads were +11.16% and +199.67% (production range +197.32% to +207.87%). Multi-row times were 3.927917, 3.959416, and 4.668083 ms, with median paired overheads +0.71% and +18.84% (production range +17.69% to +21.96%). This supersedes the historical PROFILE-only and 37.13% results for the final hook path.

After a job-local one-entry normalization cache, point-read median times were 10.671250, 11.805416, and 13.367625 ms, with paired overheads +10.42% and +24.94% (production range +20.05% to +26.64%). Multi-row times were 3.987208, 3.983541, and 4.664750 ms; paired overheads +0.10% and +17.20% (production range +16.77% to +17.91%). The cache retains at most 4 KiB of unexpanded SQL only in memory for the current job and compares bytes, not statement addresses, to prevent stale attribution on pointer reuse. This result remains substantially above PROFILE-only and must be weighed in review.

After replacing per-row mutex acquisition with a saturating relaxed atomic counter and snapshotting it for events, the same seven-pass comparison yielded median point times 10.665833 ms baseline, 11.812750 ms PROFILE-only, and 12.918208 ms production. Paired medians were +10.95% and +21.97% (production range +2.28% to +22.66%; an unusually slow baseline in one pass affected the low end). Multi-row times were 3.830709, 3.849041, and 4.055458 ms, paired medians +0.26% and +5.82% (production range +2.86% to +6.44%). As before, workload order and load were uncontrolled and this does not represent end-to-end application overhead.

## SQLite hook inventory (candidate cefda176)

Repository source audit: `grep -RInE` over Rust files in `src`, `tests`, and `examples` for `sqlite3_trace`, `sqlite3_profile`, `sqlite3_update_hook`, `sqlite3_preupdate_hook`, `sqlite3_set_authorizer`, and the corresponding rusqlite methods. This is a source audit, not a guarantee about dynamically loaded extensions or downstream callers.

- Worker writer and observed inspection readers: `src/storage/statement_observation.rs` installs STMT, PROFILE, and ROW tracing for each job and removes it afterward. `src/storage.rs` also installs and removes a commit hook for bounded execution; it is a separate SQLite hook slot.
- The runtime integration fixture in `tests/runtime.rs` installs a PROFILE hook on the worker connection to delay COMMIT. It shares the trace slot with observation: the next job replaces it, and observation subsequently unregisters it. The existing fixture therefore does not establish callback coexistence.
- `src/frontend/sql_trace.rs` installs and removes a STMT trace in test fixtures on their own connections. Benchmark-only raw trace registrations also occur in the observation module.
- No update, preupdate, or authorizer registrations were found in those source trees. The RAG read connection (`src/index/search/reader.rs`) has no registration found by this audit.

SQLite provides no API to retrieve the callback and context currently registered with `sqlite3_trace_v2`. A managed registration boundary is needed to chain known owners; uncontrolled raw installations cannot be transparently preserved. This is an unresolved design issue, not a claim that the candidate enforces exclusivity.

## Release worker comparison

On 2026-11-04, Apple M1 / macOS 26.3.1, the release example `db_observation_bench` ran against uninstrumented main `f0f719864f6b726e2efdf1ab68d66394b37fafcf` and candidate `cefda17612c73bf2dc5cdc505815e425b1317064`, without test features. Both used a disposable file database with 10,000 rows and 18 sequential worker calls per workload. The builds ran in sequence, not interleaved; system load was not controlled. The benchmark output previously labelled repetitions `instrumented` despite using the same code in each build; that label has been removed.

For 50,000 cached point reads, worker-call median was 57.2583 ms control and 58.2486 ms candidate (+1.73%); ranges were 56.2444-72.5219 and 56.4779-74.3625 ms. For 100 reads of 1,000 rows, medians were 4.0130 and 4.2301 ms (+5.41%); ranges were 3.9465-5.4084 and 4.1635-4.3263 ms. The control is a different revision and thus includes all #201 changes, not only tracing. These synthetic worker-call timings do not measure an application end-to-end request or determine the share of overhead in one. Opt-in or a cheaper path remains an option if representative measurements show a material share.
