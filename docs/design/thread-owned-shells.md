# Thread-owned shell definitions

Timed schedules and services share the `schedule` table, bounded to 64 definitions per Thread. A timed definition has exactly one timing expression; a service has neither. Both reserve a `shell_execution` through the same maintenance loop, inherit the same Thread environment, and use the same stop, drain and deletion paths. A service execution has no Run owner and cannot keep a Run live. From the service, use `shellboy message send --thread "$SHELLBOY_THREAD_ID"` to send ordinary input to its Thread.

The latest execution is the last saved reservation, independent of wall-clock adjustments. An expired disabled one-shot cannot be enabled again; create a new schedule.

A timed execution is subject to the one-hour deadline. A service is not. `service add` enables it and requests a start now; `service start` explicitly enables it again. These operations use the shared `next_at` wakeup. `service stop` disables the definition and drains its process; `shell stop` on its execution also disables it. `service remove` drains before deleting the definition. Thread deletion drains both kinds. Commands for the two kinds reject each other's IDs.

Unexpected exit or spawn failure disables a service in the terminal transaction and uses normal message admission (`Deliver::Next`) once. The fixed, owner-authored notice contains no captured output and is not subject to the external draft byte limit. It is saved as CLI sender `service:<id>` with `client_operation_id = service-ended:<execution>`. Completion only sends if the execution had not already entered `stopping`; an explicit stop racing an exit is decided by the first saved transition. A service does not restart after its own exit. The shared native start gate refuses both kinds once shutdown is accepted, including reserved executions that have not crossed the gate. Graceful owner shutdown writes a stop intent without disabling the definition or sending a message. Startup settles interrupted rows without notification and schedules all still-enabled services. It never adopts old processes; normal native lifecycle cleanup applies.

A timed occurrence whose previous execution is still active (`starting`, `running` or `stopping`) is skipped: the transaction that advances `next_at` records `last_skipped_at` and starts nothing. By default nothing else happens, so no Turn wakes. A schedule saved with `notify` containing `skipped` (`schedule add/set --notify skipped`, migration `0068_schedule_notify`, column `notify_json`; `--notify none` clears it) also sends one ordinary message per skipped occurrence in that same transaction, through the same owner-notice admission as the service-exit notice (`Deliver::Next`, not subject to the external draft byte limit). The fixed, owner-authored text names the schedule, the skipped time and the still-active execution. It is saved as CLI sender `schedule:<id>` with `client_operation_id = schedule-skipped:<schedule>:<scheduled_at>` (Unix seconds); an occurrence that already has that receipt (a re-enabled schedule meeting the same time again) sends nothing. `schedule list` shows `notify` and `last_skipped_at`. Not built: no once-per-execution rule, rate limit or batching, no catch-up runs or queueing of skipped occurrences, no notice for normal completion and no notify option for services.

The collector rotates only Thread-owned execution output. It evicts whole oldest chunks in the same transaction that appends new ones, regardless of read pins, keeping retained bytes within `shell_raw_bytes`. It keeps original sequence numbers and stream offsets. A fresh `shell read` starts at the retained boundary and reports `oldest_sequence` and the first retained byte offset for each stream that still has output when the prefix is gone; an evicted cursor receives `output_expired`. Rotation does not change retention generation; a cursor still in the retained window can continue. Run-owned output retains the stop-on-limit behavior. Terminal raw retention still runs separately.

Once terminal raw retention has collected a finished execution of a schedule or service (including one that produced no output), and a newer execution of the same definition exists, GC deletes that execution row with its raw marker ([GC](gc.md#raw-markers-and-thread-owned-executions-450)). The latest execution of each definition stays, so `list` reports it as before; `shell get` or `shell read` on a deleted older execution reports it as unavailable. Removing a definition drops its executions with it, and GC removes their leftover markers.

## Named local endpoints

A service may have an exact name (`[a-z0-9-]{1,64}`), unique within its Thread. `service set --service ID --name ''` clears it. Unnamed services have no name-based lookup. Clients resolve the name using `service.list` for the artifact's owning Thread, then request `service.endpoint` for that exact service ID. Core does not discover by name across Threads, proxy traffic, start a service on lookup, or link service and artifact lifetimes.

For each service start the supervisor creates an empty, owner-only runtime file in the data directory and supplies its path as `SHELLBOY_SERVICE_ENDPOINT_FILE`. Bind to loopback, generate a fresh unguessable token on every start, and write UTF-8 JSON `{ "port": 12345, "token": "..." }` to that existing file in place, then close it. The port must be 1–65535; the token must be nonempty printable ASCII with no spaces. The whole file is bounded to 8 KiB. Do not echo the token or put it in the service command, history, or logs. The owner unlinks the file on normal completion and when draining a stop or removal. A new execution never reuses the path or content. A read before a complete valid publication reports it unavailable; the read does not wait or start anything.
