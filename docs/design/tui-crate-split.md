# TUI crate split (#307)

## Non-goals

- No implementation before [#311 Unit 5](tui-client.md) lands. This is a proposal for the split, not a change to the #311 cutover or its scope.
- No adapter framework, generic transport or repository trait, new wire commands, second parser, or second TUI. Keep the concrete native client. Do not move behavior while moving its implementation: no policy changes to endpoints, admission, receipts, validation, startup, shutdown, or rendering.
- No new owner, launcher, supervisor, fallback, retry, persistent state, or migration. Keep the same installed `shellboy` executable and its CLI, `serve`, and protocol schema entry points. Do not split storage, compaction, indexing, or model execution here.
- Do not make every `pub(crate)` item public or turn Core utilities into a miscellaneous shared crate. Keep tests with the contract they prove; do not give a TUI unit test a dependency on the owner to regain access to private fixtures.

## First end-to-end proof

After Unit 5, take just the production Thread List read vertically through the boundary: the selected profile's endpoint, native handshake, `thread.list`, typed `Page<ThreadSummary>`, and the existing browser state and row rendering. Start at `NativeBrowser::list` and `exact` in [frontend/browser.rs](../../src/frontend/browser.rs); discard the now-obsolete `embedded(&Control)` edge, not the browser's selected-ID behavior. Move the concrete native reader into the first `shellboy-tui` library slice and have the existing browser call it. Initially the in-tree browser can still own its state and renderer; those should not be promoted to public types just to extract this read. Move them with the UI once their internal dependency closure is ready. No parallel reader or public test entry point.

Reuse the assertions from `independent_serve_browser_close_keeps_owner_until_explicit_shutdown` in [ui/threads.rs](../../src/ui/threads.rs). It currently starts two isolated `serve::run_prepared` tasks and draws through Ratatui. At the package integration boundary, launch the normal `serve` in a disposable profile, read and render synthetic rows through the production path, refresh exact IDs, and close the browser. A subsequent call must still reach that same owner instance. Preserve the separate-profile and wrong-profile assertions, without adding a mutation to the first read cut. The split is first proved when the reader compiles in a crate with only protocol and client as Shellboy dependencies, and this witness still passes together with the unchanged owner-side bounded-read tests. A hello-only crate, a mock transport, or a compile with no production caller does not prove the cut.

## Target dependency graph

```text
shellboy (binary + integration suites) -> shellboy-core, shellboy-tui, shellboy-client, shellboy-protocol
shellboy-core (owner)                 -> shellboy-protocol, shellboy-client where needed
shellboy-tui (ui/frontend/presentation) -> shellboy-protocol, shellboy-client
shellboy-client (native IPC)          -> shellboy-protocol
shellboy-protocol (wire contract)     -> no other Shellboy crate
```

The owner can also use the client library where [serve](../../src/serve.rs) or owner lifecycle helpers already call across IPC; that direction never imports TUI. The binary is the composition root, not a dependency of either library. `shellboy-tui` may use third-party terminal and runtime crates, but its only Shellboy dependencies are protocol and client. `shellboy-core` includes DB, execution, server, and owner lifecycle. This differs from treating the whole current `ipc` or `protocol` module as a leaf just because of its name.

## Landing prerequisites from #311

- **Unit 4, in full:** the landed native archive slice is not the gate. Finish selected-owner intervention and other mutations, bounded live/status/output reads, scoped notifications plus gap reload, instance fencing, and typed disconnect. Delete direct frontend DB/execution reads and the private `EngineEvent` subscription. Preserve local input and unknown operation IDs; stale Turn/execution IDs must not be used on a replacement. These changes settle the row/state types in `frontend`, `ui`, and the wire that #307 will relocate.
- **Unit 5, in full:** default native attach and one detached `serve` on confirmed absence; selected-profile/owner identity and startup diagnostics; explicit reconnect, Stop and Restart; client-only Quit/terminal loss and independent headless drain. Delete the fused `run_tui`/`run_with_*` owner lifecycle, listener and shutdown hooks, and owner-backed terminal configuration/width paths where superseded. Use the #311 cross-platform startup/termination witnesses before moving the entry point. This settles the launch signature and prevents moving a disappearing owner API into a new crate.
- **Foundation check:** confirm the Unit 3 draft/save/receipt code on the actual published base, not just a worker branch or an issue comment. Preserve its durable save and unknown-send reconciliation at the split. The inventory SHA above does not contain the Unit 3 task tip by ancestry or patch identity; it is not a landing claim. Recheck ownership and merge-sensitive paths against all landed units before implementation.

## Implementation order and evidence

1. **Sever reverse dependencies in the monolith.** After the gates, move the shared text/record definitions and test support to the owners in the map, one compiling patch per responsibility. Verify the existing sanitizer/localization and owner query tests, the focused TUI projection witnesses and `cargo check --tests --locked`. No package moves or behavior change. Check for Core-to-TUI references in production *and* tests before continuing.
2. **Make protocol a leaf.** Move the actual wire definitions, schema inputs and pure validators; stage owner-specific parts within Core first if a wire type still contains one. The current schema generator uses more than `Command`: preserve its result catalogue, optional owner version, schema metadata and version. Verify byte-for-byte schema output, catalogue tests, deserialization/validation and existing client/owner round trips. No protocol bump for a move. Keep a single definition; do not accept `protocol -> core` as a temporary edge.
3. **Extract the concrete client without a TUI move.** Move endpoint/handshake and call-side code once the protocol leaf is usable. Leave listener, owner admission and identity publication in Core. Run selected-endpoint, denied/mismatch and lost-response/receipt tests, plus the existing CLI/`serve` acceptance. Keep package checks for all affected targets green.
4. **Compile the browser slice separately.** Land the first proof above. The existing binary still drives the only production TUI; only the implementation location of the native browser reader changes. Check the new package alone and the existing independent-owner browser integration witness. Keep any remaining monolith UI dependency pointing toward TUI, not the other way around; if the boundary requires an owner import, stop and finish that #311 removal first.
5. **Move the rest of the TUI and finalize build topology.** Transfer `ui`, the client frontend and `presentation` together after removing the remaining Core imports. The existing executable composes the Core library and the TUI; keep CLI spelling, config resolution, packaged docs, test registration and release binary name stable. Update workspace commands, lockfile, language/test-layout inventory and CI paths in the same compiling patch. Verify `cargo check --workspace --tests --locked`, Core-only and TUI-only package tests, unchanged wire schema, and the existing real binary PTY/shutdown and three-OS acceptance in CI. No installed-binary changes. Do not declare the boundary complete until `cargo tree -p shellboy-tui` shows no Core or SQLite edge and `cargo test -p shellboy-core --lib --locked` does not build TUI.

The reason to split is build isolation, not deletion or line count. #307 records an 8 GB development machine and swap exceeding 31 GB; it does not establish that rustc caused the swap incident. A name-filtered `cargo test` today still compiles the whole library test crate. With the split, an owner implementation-only change does not require TUI in a Core-only check, and a TUI-only edit can test against already-built protocol/client dependencies without rebuilding Core. Wire/client changes invalidate their consumers; the shipping binary and end-to-end tests still build and link both sides. Splitting the Rust compilation unit makes a lower per-rustc peak plausible; the largest remaining crate, concurrent jobs, linker and cold workspace tests still matter. Cold builds can get slower (more links, Core lib and test variants). No new measurements were made and no memory percentage is promised. Accept the design by the direction of dependencies, one owner per contract and actual independent package build graphs, not the size of the diff.
