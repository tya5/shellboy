# Core reads for Analytics (#419 design)

## Non-goals

No implementation, money, price, estimates, causal savings, synthetic norms, provider calls, or provider bodies. No new storage or index without a separately recorded need. No compatibility alias, generic analytics RPC, cursor store, fingerprint, automatic full-history walk, per-Thread fan-out, or new Studio behavior in this issue. Do not map a usage bucket to a conversation anchor by timestamp proximity.

## Evidence and admission

Studio's [Analytics design](https://github.com/tya5/shellboy-studio/blob/522d18e6b07e2f83acf5546620a278d290f1ca87/docs/design/analytics-improvement.md) pins Core `46212b5391e2d486efec770291359a2ba671fa01` (protocol 26). Source and guide line references below are to that pin, not an installed owner. This is source analysis, not a measurement. Prefer an external presentation/analysis component, then a thin client over existing owner reads, and add a generic bounded Core read only where those cannot answer without an export, a fan-out, or a false join. Do not export private history just to make an external component possible.

Use the [list and observation contract](list-observation-contract.md#page-and-observation-fields). #416 Unit 1 landed at `372cde528ee67e85dce6140ebd2c721940c5d5b5` (protocol 30). Its [published schema](https://github.com/tya5/shellboy/blob/372cde528ee67e85dce6140ebd2c721940c5d5b5/docs/reference/protocol.schema.json) and [Record page fields](../guides/cli-reference.md#record-page-fields) confirm top-level `items`, effective `limit`, typed `filters`, and `next_cursor` where resumable. `UsageBreakdownResult` still has `group_limit` and `next_cursor` but no `filters`; the filtered-mode echo below is a proposed addition, not a shipped field. `compact.list` has `items`, `limit`, `filters`, `more`, `period`, and `coverage` without `next_cursor`. Grouped usage remains a grouped-statistics exception: an effective `group_limit`, not an ordinary record-page default of 50, and continuation via `next_cursor` while `more`, even for empty `items`. Where an approved new usage selector needs an echo, add typed `filters` from effective selection, not serialized args. Keep existing usage fields; no rename of `group_limit`, no invented scan counters or cursor on a capped report. For computed counts pair `x_count` with `x_count_exact`, and name the relevant population; absence is not zero. An exact count of known records in a candidate window does not prove full period coverage or that all recorded usage values are known.

### 1. Saved model and connection filters — Build smaller

**Need:** Show usage over time or by Thread for a chosen saved model, connection, or both.

**Existing read:** `usage.get group_by=model` shows saved model buckets within a scope; an exact attempt read can show a known attempt, and some grouped rows report rate observations by connection, not a connection-filtered token series. Those aggregates have lost the joint model/profile/time/Thread assignment. Filtering the returned groups cannot recover it. Sources: `src/control/db/usage_status.rs:78`, `src/usage_totals/breakdown.rs:325,348,735`; `docs/guides/cli-reference.md:180,1040`.

**Contract:** Extend only the existing grouped conversation mode (`hour`, `day`, `thread`, `model`) with optional exact `model_id` and `profile_id` (`--model`, `--profile`, no aliases). `profile_id` is the saved connection/profile ID, not a display name, credential, active config lookup, or provider ID. AND the supplied dimensions with the existing scope and half-open period, before grouping. Keep existing optional Thread/Run/Turn scope and descendants rules; reject these selectors for exact-attempt, ungrouped totals, or `shell-exit`. No catalog lookup, regex, prefix matching, list of values, or assignment inference. A nonempty saved ID is literal, even when no longer configured; a value that looks like a legacy sentinel is not missing unless the writer or migration proves it. The pinned schema has non-null text and migration 52 preserves the preexisting IDs verbatim (`migrations/0052_unified_model_attempt.sql:3,11`); do not promise a generic legacy class. If a persisted empty value exists, count it as unassigned for that dimension, not as an alias for a model/profile.

- The usage owner validates each requested ID as nonempty and at most 512 UTF-8 bytes (existing grouped usage ID echo bound, `src/usage_totals/breakdown.rs:855`); reject oversize, never truncate or case-fold. `filters` describes resolved scope and period, grouping and timezone. Echo a new selector only from a matching saved, shareable ID already projected by the usage reader; otherwise set `filters.model_id_omitted` or `filters.profile_id_omitted` as appropriate, including on an empty page with no such witness. Omission is about the echo, not application of the predicate. Never reflect arbitrary nonmatching input to obtain a stable client key. Owner-derived defaults, not guessed client defaults. No cursor or payload in the echo.
- Keep `items`, `group_limit` (1..=168, default 168), `more`, `next_cursor`, `scope_complete`, `scan_truncated`, and `statistics_scope`. Reuse the owner/cursor filter binding, now including both selectors. The cursor advances by the last examined candidate after in-window group paging, not by the last matching attempt. Keep `known_sum`, `unknown_count`, and `overflow` on usage values. A group can recur in later windows; percentile and ratio values are not combinable by averaging.
- With a dimension selector, make the `coverage.summary` reason explicit (proposed `not_attributed_by_usage_filter`); the compaction section is unavailable and `total` must say it is conversation-attempt-only, retaining the current model-group shape rather than implying zero summaries. Don't execute the summary scan in this mode. An unfiltered walk can still report the existing separate compaction counts or usage; it is not part of the filtered result. No new summary-profile attribution even if individual summary attempts happen to carry a profile; group attribution and full accounting have not been established.
- To disclose unassigned data, only report `unassigned_model_count` and `unassigned_profile_count` with corresponding `_exact` flags for the same examined live/in-period/in-scope conversation candidate window **before** the new dimension predicates, only if the implementation confirms a recognized missing identity representation. Once computed, emit exact zero as well as positive counts. Count each dimension independently (the populations can overlap); absent pair means not computed, and a count of zero is not evidence about other windows or missing starts. Count once per candidate, not once per returned group; repeated group pages for the same window are not separate observations. No legacy inference, separate inventory, or extra SQL count.

**Owner and cost:** `usage.get` validation owns inputs; the grouped usage reader owns the echo, cursor, omission and count facts. The saved attempt writer remains authoritative for both IDs. Candidate SQL already projects `profile_id` and `model_id` and takes an exclusive `(rowid, watermark]` range for `kind='conversation'` capped by `ROW_LIMIT=10,000` plus lookahead (`src/usage_totals/breakdown.rs:7,98,659,671`). Migration 52's existing `attempts_by_kind` index can seek by kind and rowid; an implementation must verify sparse-selection work on the real schema, not assume a date or profile seek from `LIMIT`. Apply two comparisons inside the already bounded pass after scope/time checks; no extra source rows, joins or count queries. Preserve the 31-day elapsed bound, grouped cap and frame budget. Filter scarcity can yield empty pages, not cheap full walks. This earns a generic read because the current grouped outputs cannot answer exactly; do not extend ungrouped query families or compaction attribution.

### 2. Ranked trends and Turn distribution — Build smaller (client only)

**Need:** See which Threads contributed to a chosen time bucket and inspect a known Turn when an authoritative Turn ID is available.

**Existing read:** `usage.get group_by=thread` accepts the intersection of that bucket and the selected period as `[since,until)`; it already gives a Thread key for each returned group. `usage.get --turn TURN` is a separate exact-scope read for a known Turn, not discovery or a period-wide Turn distribution. Some groups provide a validated `max_attempt` tuple, not all Turn memberships. No join of the independent hour/day and Thread pages can reconstruct either Turn identity or a Thread's period series. Sources: `src/usage_totals/breakdown.rs:325,335,348,735,824`; `src/control/db/usage_status.rs:88`; `docs/guides/cli-reference.md:1040,1047,1063`.

**Smallest bounded contract:** Keep the existing thin-client walk for one selected bucket: same scope and fixed offset, explicit clipped bounds, `group_by=thread`, `limit` within the existing 168 group cap, `cursor` only from this walk. Return the existing `items` and `key` (Thread), `group_limit`, `more`, `next_cursor`, `scope_complete`, excluded starts and current-window coverage; do not add a Core field or imply this grouped report has ordinary record-page shape. Client stores the effective filters with the walk and retries only by user action; it stops at Studio's existing 64-response run and 2,000-group page-boundary threshold and can explicitly Continue. A partial rank is labeled partial, not a top-of-period. Rank the requested measured fact only after merging non-overlapping candidate windows, and only claim exactness for the explicitly covered population. Open exact `thread.get`/Conversation by Thread ID; unavailable stays unavailable, no substitute. For an already validated Turn ID the client can request one `usage.get {turn_id}` and keep existing coverage, verifying Studio's argument path separately. Neither fact reveals a visible path anchor.

**Owner and cost:** Core's existing candidate and group limits apply; one deliberate bucket walk, not one read per Thread or Turn. Where existing unfiltered compaction coverage is required, the second candidate window (`ROW_LIMIT`, `COMPACTION_PAGE_BYTES=4 MiB`) is separate from conversation work; summary membership queries are distinct and those candidate caps do not themselves prove a member-row bound. Sources: `src/usage_totals/breakdown.rs:358,678,750,855`. Client owns ranking and follow-up navigation, not facts. Reject both multi-key scans and new cross-Thread Turn distribution for now. Reconsider only if a shipped one-bucket flow demonstrably fails a named task: require a bounded existing seek or a separately justified indexed path, an explicit Turn population (all Turns or only those with in-period eligible attempts), stable exact Turn/Run/Thread references and evidence for any visible-node anchor. No guessed buckets or marginal joins.

### 3. Summary savings — Do not build

**Need:** See what changed after adoption without implying that a summary alone caused the difference.

**Existing read:** `compact list` already reports the observed trigger input where recorded and the first owner-proven later request ID/input for an applicable adopted summary. `src/readback/compact.rs:259,449,554` associates by adopted replacement and later attempt. The guide defines null versus not applicable, inherited forks, and multiple adoptions sharing the same later attempt (`docs/guides/cli-reference.md:840,846,855`). `usage.get --attempt` can inspect that exact attempt (`:180`); neither API proves a matched counterfactual or isolates changed tools, context, model, or subsequent inputs.

**Smallest bounded contract and cost:** Keep `compact list` as the existing capped Thread report with `limit` (default 50, ceiling 200), `filters`, `items`, `more`, `period`, `coverage` per #416, no `next_cursor` or whole-period count. Use the existing source result cap `min(4 * limit + 1, 801)` and at most `limit` replacement candidates for post-input lookups (`src/readback/compact.rs:263,366,449`), with no added SQL or count work. These are candidate/result caps, not a new claim that every existing SQL path seeks or has bounded physical scan work. The Core compaction reader owns the trigger, adopted/link/coverage and null facts. Studio may subtract two observed reported inputs in the same units when both exist, label that an observed signed change, preserve scope and partial/unknown flags, and neither sum effects sharing an attempt nor impute absent data. No new fields, owner or computation in Core. Reopen only with a recorded need and a proven bounded comparator on the same attributable input basis that can identify what stayed fixed and what changed; provider usage from two requests alone is insufficient.

### 4. Longer baselines — Do not build

**Need:** Compare the current period to a clearly named reference without turning recent history into a claim about what is usual.

**Existing read:** Use two independent grouped usage walks with the same filters, group, fixed offset and comparable elapsed/calendar slots; current and previous windows each stay within the 31-day cap. A partly elapsed last bucket gets the same cutoff in its paired slot. This answers the previous-period task; it does not establish a reference distribution. Sources: `src/usage_totals/breakdown.rs:66,335,829`; `docs/guides/cli-reference.md:1058,1063`.

**Smallest bounded contract and cost:** No new request or response fields. Keep the existing `limit`/`group_limit`, unchanged filters on each continuation, `items`, `next_cursor`, existing scan/scope coverage and known/unknown/overflow facts per walk. The owner supplies saved observations and candidate caps, the client aligns and labels the comparison under Studio's existing walk budgets. Two separate walks are not an atomic snapshot. Show a change only for comparable covered observations and a valid denominator; a missing slot is not zero. Do not pool per-page percentiles, span multiple months by unbounded iteration, fit a model, or add an owner baseline cache. If the previous-period view later fails a concrete task, define a finite cohort with membership, date/zone, sample unit and coverage first; attach no `x_count_exact` to an uncomputed population and require bounded source work before asking for a new read.
