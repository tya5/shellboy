# Thread artifacts

An artifact is a Thread-owned record with an independent ID and Core-authored UTC creation and update timestamps. Its versions append from 1, carrying an opaque URI, title, optional MIME and UTC creation timestamp. URI and title require 1 to 2,048 and 1 to 256 UTF-8 bytes respectively; MIME is optional and at most 128 bytes. The owner rejects oversized strings and never normalizes them. Omitted update title keeps the prior title; omitted MIME saves no MIME for the new version.

The existing owner database writer owns both tables and commits them with the mutation receipt. The existing Thread change hint wakes `events.wait` clients, which reread on a matching hint or resync. There is no artifact-specific publisher, queue or worker.

`artifact.list` seeks by descending update time and ascending artifact ID and returns the latest metadata per item. Without a scheme, `thread_id` is required and the list is scoped to that Thread. With a scheme, the owner filters by the lowercase scheme of the current version, includes only live, non-archived Threads, and optionally narrows to `thread_id`. Each scheme-list row projects the owning Thread's `owner_title` in the same bounded indexed SQL read that selects its membership, ordering and latest metadata; clients do not need a second title lookup. This value is present only on scheme-list rows and is omitted from ordinary per-Thread lists and artifact history. `artifact add` and `artifact update` save `artifact.current_scheme` in the version transaction (null for a schemeless URI); fork/rewind copies it with the versions. The cross-Thread read uses `(current_scheme, updated_at DESC, id)` and binds the scheme and optional Thread to its cursor. With a Thread filter, the reader uses the Thread index instead. Each scheme page examines at most 128 candidates, plus one lookahead; an empty or short page may have a `next_cursor` that resumes after the last examined candidate. `artifact.get` returns one version when selected, or the latest metadata and a descending page of version numbers and timestamps. Both paged reads allow 1 to 32 rows; cursors bind to the query kind and owning ID, including the order for list cursors. Pages are live reads, not snapshots: refresh from page one to see inserts or updates that sort before the current cursor.

Archive keeps artifacts. Fork and the rewind child copy the complete metadata snapshot with distinct artifact IDs in the existing Thread copy transaction; rewind does not change the original's inventory. Confirmed Thread deletion removes roots in the existing tombstone transaction, with versions removed by foreign-key cascade; canonical `thread.delete_preview` counts all roots in the selected Threads. The finite UI observation reads at most 1,025 indexed roots to report an exact count through 1,024 or an incomplete observation with a lower bound of 1,024. This does not limit artifact registration. Neither deletion nor `artifact.remove` touches referenced content. The CLI joins schemeless relative paths, and the relative folder of a `shellboy-app:` URI, to its own working directory before sending add/update, dropping `.` components lexically without resolving symlinks or changing the treatment of `..`. Registration stores the URI as given: add, update, list and get do not interpret schemes or MIME, resolve paths or check existence, and the owner never fetches, copies, previews or cleans up content.

## Reading content (#445)

The URI scheme of a version says what it shares, and only the owner applies that rule, so every client, including one on another machine, reads content the same way through `artifact.read`.

| Version URI | Meaning | `artifact.read` returns |
|---|---|---|
| `shellboy-app:` + absolute folder path | The folder is a web app; its entry is `index.html` | A regular file under the folder, named by a relative `path`; a path or link that leaves the folder is refused |
| `file:` URI, or a schemeless absolute path | That one file | That file only; a `path` is refused |
| `http:`, `https:`, a relative path, anything else | External or unknown | Refused; the owner never fetches |

`artifact.read {thread_id, artifact_id, version, path?}` resolves only that exact saved version of an artifact in that Thread, then returns one regular file as `{artifact_id, version, path?, raw_bytes, base64}`. The scheme name is compared without case. A `file:` URI must name a local path. A folder `path` is relative and may not contain `..`, a root or a drive; the owner resolves every link in the folder and the path, and refuses a resolved file outside the resolved folder, so links that stay inside are followed. The rule protects against a page or client asking for paths outside the folder. The check-then-open race is an approved exception ([#445 decision](https://github.com/tya5/shellboy/issues/445#issuecomment-7192525049), recorded in the [decision log](../development/decisions.md#artifact-reads-445)): swapping links inside the folder needs write access that only the same local user or that user's model shell has, and both can already read those files, so the race grants nothing the rule withholds. Only local files are read. Every form is first resolved to a filesystem path (a schemeless path as given, a `file:` URI after conversion, a `shellboy-app:` folder, and that folder joined with the relative path), and one local-path rule then normalizes a Windows verbatim drive path such as `\\?\C:\work` to `C:\work` before checking and using it. The rule refuses, before any filesystem access, a path that still starts with two separators of either kind (`\\server\share`, `//server/share`, `\\?\UNC\server\share`, and the Windows `\\.\` device namespace), contains a control character, or (on Windows) has a reserved device name such as `CON`, `NUL`, `COM1`, `LPT1` or a superscript alias like `COM¹` in any component: `invalid_argument` with `path_not_local`. A `file:` URI is also refused as `uri_not_readable` when its authority is not empty or `localhost`, checked on the raw text (where a tab, newline or carriage return refuses the URI) and after URL parsing. Special files never block a worker: Unix opens without blocking, Windows checks the type before opening; either way the opened handle must be a regular file and is the handle read, otherwise `target_unavailable` (`not_a_file`). Failures are typed: `invalid_argument` with `details.reason` `uri_not_readable`, `path_not_local`, `path_required`, `path_not_allowed` or `path_outside_folder`; `target_unavailable` for a missing version (`thread_not_found` for the Thread) and, with `details.reason` `file_unavailable` or `not_a_file`, for a missing or unreadable file; `input_limit` with `file_too_large`, `raw_bytes` and `limit_bytes`.

A read is bounded by one effective limit: the smaller of `limits.attachment_file_bytes` and the largest file whose base64 reply to this request, envelope included, fits one 8 MiB frame (a little under 6 MiB). The owner derives it from the frame size and the request's own fields, and refuses a larger file with `input_limit` (`file_too_large`, `limit_bytes` = that effective limit) from its size before reading or encoding it, so an admitted reply never fails at the transport. The lookup is one indexed row on the database worker; the file is opened and encoded on the existing attachment blocking-file pool within `io.file_prepare_timeout_ms`, never on the UI thread. It is a receipt-free observation: owner shutdown or a disconnected caller ends it, and a started read finishes on its worker. There is no cache, copy, write, remote fetch, type sniffing, directory listing or change event; how content is shown is the client's choice from the file extension.
