# Thread artifacts

An artifact is a Thread-owned record with an independent ID and Core-authored UTC creation and update timestamps. Its versions append from 1, carrying an opaque URI, title, optional MIME and UTC creation timestamp. URI and title require 1 to 2,048 and 1 to 256 UTF-8 bytes respectively; MIME is optional and at most 128 bytes. The owner rejects oversized strings and never normalizes them. Omitted update title keeps the prior title; omitted MIME saves no MIME for the new version.

The existing owner database writer owns both tables and commits them with the mutation receipt. The existing Thread change hint wakes `events.wait` clients, which reread on a matching hint or resync. There is no artifact-specific publisher, queue or worker.

`artifact.list` seeks by descending update time and ascending artifact ID within one Thread and returns the latest metadata per item. `artifact.get` returns one version when selected, or the latest metadata and a descending page of version numbers and timestamps. Both paged reads allow 1 to 32 rows; cursors bind to the query kind and owning ID, including the order for list cursors. Pages are live reads, not snapshots: refresh from page one to see inserts or updates that sort before the current cursor.

Archive keeps artifacts. Fork and the rewind child copy the complete metadata snapshot with distinct artifact IDs in the existing Thread copy transaction; rewind does not change the original's inventory. Confirmed Thread deletion removes roots in the existing tombstone transaction, with versions removed by foreign-key cascade; canonical `thread.delete_preview` counts all roots in the selected Threads. The finite UI observation reads at most 1,025 indexed roots to report an exact count through 1,024 or an incomplete observation with a lower bound of 1,024. This does not limit artifact registration. Neither deletion nor `artifact.remove` touches referenced content. The CLI joins schemeless relative paths, and the relative folder of a `shellboy-app:` URI, to its own working directory before sending add/update. Registration stores the URI as given: add, update, list and get do not interpret schemes or MIME, resolve paths or check existence, and the owner never fetches, copies, previews or cleans up content.

## Reading content (#445)

The URI scheme of a version says what it shares, and only the owner applies that rule, so every client, including one on another machine, reads content the same way through `artifact.read`.

| Version URI | Meaning | `artifact.read` returns |
|---|---|---|
| `shellboy-app:` + absolute folder path | The folder is a web app; its entry is `index.html` | A regular file under the folder, named by a relative `path`; a path or link that leaves the folder is refused |
| `file:` URI, or a schemeless absolute path | That one file | That file only; a `path` is refused |
| `http:`, `https:`, a relative path, anything else | External or unknown | Refused; the owner never fetches |

`artifact.read {thread_id, artifact_id, version, path?}` resolves only that exact saved version of an artifact in that Thread, then returns one regular file as `{artifact_id, version, path?, raw_bytes, base64}`. The scheme name is compared without case. A `file:` URI must name a local path. A folder `path` is relative and may not contain `..`, a root or a drive; the owner resolves every link in the folder and the path, and refuses a resolved file outside the resolved folder, so links that stay inside are followed. This check sees the folder at read time and does not isolate a same-user process that swaps files during the read. Failures are typed: `invalid_argument` with `details.reason` `uri_not_readable`, `path_required`, `path_not_allowed` or `path_outside_folder`; `target_unavailable` for a missing version (`thread_not_found` for the Thread) and, with `details.reason` `file_unavailable` or `not_a_file`, for a missing or unreadable file; `input_limit` with `file_too_large`, `raw_bytes` and `limit_bytes`.

A read is bounded by `limits.attachment_file_bytes` and by one reply frame: the base64 text alone must fit 8 MiB, so at most 6 MiB of a file is returned, and a reply whose envelope still exceeds the frame fails with the transport's `input_limit`. The lookup is one indexed row on the database worker; the file is opened and encoded on the existing attachment blocking-file pool within `io.file_prepare_timeout_ms`, never on the UI thread. It is a receipt-free observation: owner shutdown or a disconnected caller ends it, and a started read finishes on its worker. There is no cache, copy, write, remote fetch, type sniffing, directory listing or change event; how content is shown is the client's choice from the file extension.
