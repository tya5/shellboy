# 添付の所属・再送位置の是正

## Current-only contract (Issue #33, 0.2.0)

Before 1.0.0, release-specific backward-compatibility paths are not part of the contract. The general schema migration runner, `user_version`/ledger validation, and protocol-version checks remain. Earlier sections describing an old-format fallback, deprecated alias, metadata repair, or compatibility shim are historical and superseded by this section; they must not be used to justify a runtime fallback.

2026-10-25採用の添付所属・出典・通知契約。添付を要求末尾のuser messageへ一括追加していた既存driverを修正する。情報の削減や画像の送信停止で症状を隠さない。初期の仕様・詳細設計・CLI・引継ぎ資料は非同梱。

## 保存と採用

確定参照はsource nodeを必須にし、そのpayload.contentの順序付き `attachment_ref` 要素を所属の正本にする。人間の送信はuser nodeと参照を同一transactionで確定する。CLI追加はoperation IDと認証済みshell／外部CLIの区別を持つ独立した補助nodeを保存する。人間のmessage receiptを作らず、受付結果と一覧にsource_node_idとdelivery_statusを返す。

CLI nodeは受付時に採用経路へ割り込ませない。専用delivery台帳でaccepted/held/applied/cancelledを追跡し、完全tool group後・inflight要求のない安全境界で採用する。停止／復旧待ちは保留、削除では取消。未採用nodeもGC rootで保護する。forkは採用済みの元経路だけを共有する。

受付時の `target_run_id` を固定し、heldを再採用できるのは同じ生存Runの明示retry後だけとする。停止済みRunの保留は新Runへ移動せず、新しい指示を待たせない。起動元が別Threadの場合も元tool groupの完了を待ち、受け付けの遅い操作が追い越さない。起動元が停止し元groupが未完なら保留を維持し、新しい要求を阻害するpendingから除外する。起動復旧・通常終了でも割当を保持する。元Runが記録されていないlegacy参照へ架空のRunを割り当てない。

## API入力と版

本文変換キャッシュはsource IDと未展開attachment_refを保持し、毎回最新のファイル読取り結果を元の要素位置へ展開する。新しい要求へ古い画像bytesを再利用しない。APIにはローカルmarkerや独自fieldを渡さない。CLI補助messageは画像／fileを受け付けるuser roleを使用し、Shellboy操作であることと追加元を本文内メタデータで明記する。

要求manifestは添付ID・source node・source要素位置・展開先API item/content位置と範囲・hash/read状態・初回反映か履歴再送かを記録する。原文要素がない、重複する、選択経路外である場合はHTTP開始前に準備エラーとする。末尾への付替えfallbackを設けない。

元位置のメタデータに今回読取りの版と初回／再送を示す。正常完了した同Thread・同添付IDのhashを基準に変更を判定する。同パスでも別IDは別添付。変更通知は履歴末尾の安全境界に独立したShellboy通知として置き、ID・source・比較hashと決定的update IDを持つ。失敗／中断後は同じ未処理更新、正常完了後は新規更新として再通知しない。baseline更新は応答の正常完了と同一transactionにする。不在／除外は元位置に状態を残し、コンパクションで置換されたsourceの実体は送らない。

## 既存データ

Historical migration-4 attachment-origin reconstruction is superseded by Issue #33. Current attachments require a real source node and ordered source reference elements. Missing provenance is an error; do not fabricate a legacy recovery source or infer an insertion position. General schema migration infrastructure remains separate from runtime attachment validation.

## 検証

A24〜A28は自然言語応答の印象では判定せず、実HTTP clientが送信した入力と永続manifestを比較する。再送・キャッシュ再利用／破棄・モデル変更・fork・再起動、CLI追加の全tool result後配置、保留／取消、変更／失敗retry、不在／除外／圧縮、破損参照のHTTP開始禁止を対象とする。通常テストは専用fixtureとloopback HTTPを使用する。実proxy試験を行う場合は利用者が明示指定した接続先だけを使用する。

## 準備snapshotと未採用の人間送信（M1/C4/C7）

Driverのnextで取得したselection revisionを添付準備のDB snapshot入口でも照合する。途中の添付受付によるrevision競合は外部副作用なしでnextへ戻り、同じ受付messageを採用した最新経路から準備し直す。既存の単独prepare操作はAPIを変えず、Driver専用のrevision付き入口を追加する。

人間のaccepted/held receiptに所属し、まだ経路に採用されていないuser sourceは、既存CLI deliveryの未採用sourceと同様に今回の実体展開対象から外す。別Turn・保留中のsourceを最新発言へ付け替えず、受付やselectionを削除しない。source payloadの欠損・重複参照は先に検査し、receiptで説明できない経路外sourceも準備エラーのまま維持する。単なる経路欠損を無条件に競合へ変換しない。

attempt採用時のCAS不一致/OperationConflictだけを再準備対象とする。恒久的InvalidState等をfalseへ潰して反復せず、保存済みTurnをrecovery_waitへ移す。HTTP client構築失敗も同じ復旧境界へ保存し、自動の再kickで同じ構築を無制限に繰り返さない。SaveFailedは共有分類どおり保存障害として扱う。 next内部の添付採用などsnapshot成立前の恒久失敗にも同じ境界を適用する（PR1-5）。失敗した準備transactionはrollbackし、まだliveの同Runに既存の準備中TurnがあればそのTurnを、なければ今回の準備失敗を表すTurnを一つだけ作成してrecovery_waitへ移す。完了済みTurnを改変せず、既受付本文・source・rawは保持し、accepted添付はheldへ保留する。選択競合だけは再snapshot可能とし、保存障害は復旧状態の捏造ではなく既存の停止経路へ伝播する。公開CLI・受付割当・永続schema・元位置の契約は変えず、新しいevent/worker/queueを追加しない。

`src/control/driver/preparation_tests.rs` はnext→人間添付受付→prepareを明示順序で並べ、再snapshot後の実loopback HTTP inputと保存manifest/source/要素位置を照合する。held sourceの延期、壊れた参照/説明不能な経路外sourceの拒否、採用CAS競合の非復旧化、恒久adopt失敗のrollback/recovery、client構築失敗後の有限終了を検証する。時刻待ちで競合を推測せず、実proxyや既定DBは使わない。

## 人間の下書き要素順（M3）

本文と添付の順序・出典は本書の採用契約とする。下書きの本文と添付を別々に保持するだけでは「本文前→画像→本文後」を入力できず、sourceを保存しても順序を復元できない。

UI下書きは既存text/filesを維持し、添付へoptionalなbyte位置を加える。位置付き添付はtext内の単一graphemeのmarkerで示し、caretが前後へ移動できるようにする。marker自体はモデルへ送らない。旧下書きの位置なし添付は従来どおり本文末尾と解釈する。通常文字として入力した同じglyphは、対応する添付位置がなければ本文のまま扱い、添付を推測しない。挿入・削除はmarker位置も更新し、markerを削除した場合はその下書き添付も外す。

Frontendはmarkerを除いた本文と、元の要素順に並ぶ添付・本文byte位置をControlへ渡す。Controlは位置数、非減少順、範囲、UTF-8境界を検証し、receipt/source/ref/選択の受付transaction内で ordered content を作る。保存後にモデルへrefを移動させない。既存String/files入口とCLI message/attachment操作は変更せず、従来の本文末尾・専用source規則を維持する。新しい位置付き入口は既存受付の局所拡張とし、schema/table/worker/eventを増やさない。

送信snapshot、保存draft、明示retryは同じmarker/位置を保持する。編集・保存原文復元ではcanonical source contentを経路順に読み、input_textとattachment_refの相対位置からmarkerを再構築する。SQLのID順やモデル推測から添付順を作らない。既存添付IDを別sourceへ付け替えず、編集は元のfork規則どおり新しいsource/refを作る。

内部の `DraftContent` はUI表現から切り離した本文・添付位置を一括検証する小さな値型とする。position数は既存添付数と一致し、marker数は既存draft byte上限に収まる。既存String/filesの末尾配置と同じ要求には新しいfingerprint要素を足さず、保存済み同operationの再送互換を維持する。位置の異なる要求は同一扱いにしない。UI待機中の画像leaseは受付workerも保持し、現在の下書きからchipを外しても実行中の受付が使う画像を途中回収させない。

本文全体を上下キーで別の依頼へ置き換える間は、未送信添付をその新本文の末尾とする。Downで元の下書きへ戻る際は保存した完全snapshotから元位置を戻す。slash判定ではtyped添付markerを除いた本文を見る。command clearは本文だけを除去して位置付きchipを残し、失敗時はU5の完全snapshot/CASで元の本文・位置へ戻す。これによりchipがあっても /attachments や /detach を使え、添付を失わない。

## 最終source本文の一度だけのINSERT（M12）

添付のsource node本文は追記のみで扱う。添付IDとUTF-8位置順をsource INSERT前に確定し、最終content（attachment_ref要素を含む）とhashを一度だけ保存する。登録helperは既存sourceの参照IDとplanのfile順を検証し、attachment_ref/selectionとmanaged lifecycleのmetadataだけ登録する。node payload/hash/revisionを書き換えない。新規かコミット済みかを別DB接続や新stateで判別する方式、revisionを上げて本文を後付け変更する方式は採らない。

CLI AttachmentAdd、human draft送信、編集forkの3経路は、既存operation transaction内で最終source INSERTとmetadata登録をまとめる。失敗時は同じsavepoint/transactionで戻り、receipt再送、source/provenance、位置、選択CAS、fork共有、索引許可、replay cacheの契約を維持する。append位置の既存content表現とfingerprintも維持する。

Rust補助API AttachmentService::add/add_txは製品wire APIではないが、署名を保ったまま登録専用の安全な境界にする。source payloadが計画した数・順序の一意なattachment IDsを既に宣言している必要があり、本文に添付参照のない既存nodeへ後付け追加する呼出しは拒否する。既存nodeがコミット済みでも本文は変更されない。新表/worker/公開commandは追加しない。fixtureも最終sourceをINSERTする実運用と同じ手順へ移す。

## 更新通知の保持と成功後の再送（M6）

更新通知の永続的な根拠は、HTTP開始前に保存する各model_attemptのinput_manifest_jsonとする。添付ID・source node・前回成功hash・今回hash・changedを保持し、決定的update IDを再構成できる。失敗／明示retryは同じ未処理更新として通知し、正常完了とbaseline更新を同じtransactionで確定する。

正常完了した更新通知の文面を、後続要求のcanonical DAG本文へ追記して再送する案は採らない。後続モデル入力には元source位置の今回読取りmetadataを置くが、以前の更新が新たに起きたようには通知しない。「更新の事実が通常会話本文のreplayには残らない」という指摘自体は正しく、永続監査記録が失われることとは区別する。元本文と別に保持するDD §3.1の契約はattempt manifestで満たし、既存の不変DAG・selection・compactの意味を変更する新しいevent/table/workerは足さない。

正常完了後の別要求とowner再起動を経ても元attemptのmanifestが保持されること、および後続要求が同じ更新を再通知しないことを実ownerとloopback HTTPで照合する。将来、過去の版変更をモデルが通常履歴から直接説明する要件を追加する場合は、監査情報への読取り導線と通知の再送・費用・compactionの扱いを一緒に再検討する。現在の選択内容を過去版bytesの保存保証と扱わない。
