# 送信用履歴cache

送信用履歴キャッシュ・通信中断・再送選択の採用設計。元のnode JSONとAPI送信itemを分け、元履歴は変更しない。APIの呼出し回数、Turn/Run、receipt、generation採用境界は変更しない。初期の再送仕様資料は非同梱。

既存driverは要求ごとに選択経路の全payloadを読んでJSON parseしていた。全Threadで共有する `ReplayCache` をControlに一つ置き、DB workerのsnapshot確定中に選択経路metadataを照合する。cacheはDBの代替正本にせず、同じtransactionで観測したnode ID・payload revision・tombstoneを確認した結果だけを要求へ使う。API直前のselection/profile/generation CASは従来どおり残す。

cacheの文脈はThread ID、selection revision、profile revision、profile/model、reasoning epoch、固定adapter/tool schema版を持つ。同じ文脈と同じ経路はhit。profile/model/epoch/adapter/tool変換条件が変わらず既存経路の完全なprefixへ通常appendした場合は、既存nodeの変換済みitemをArcで再利用し、新しいsuffixだけをDBから読んで変換する。経路の置換・巻戻し・compaction・実profile/model/epoch変更・同経路のselection revision変更は対象Threadを再構築する。fork先は別Threadのentryであり元Threadのentryを変更しない。profile revisionは観測・API直前CASのため記録するが、effort/cwdだけの変更では全履歴を再変換しない。要求ごとのeffort等の値は履歴itemへ埋め込まずrequest設定として組み立てる。

API itemは immutable な変換結果として保持する。reasoning itemは対応nodeのepochが現在のepochと一致するときだけ送信対象へ入れる。model A→B→Aでもepochを戻さず、旧opaqueを復活させない。tool call/result、item ID、phase等の元API項目は維持する。event envelopeの内部event_idだけを送信用copyから外し、DB JSONを更新しない。暗号化reasoningを平文へ変換・索引化しない。

`cache.history_bytes` を全Threadの保持entry合計へ適用し、Thread単位LRUで回収する。重みはUTF-8 serialized長だけでなく、Value配列/文字列capacity/JSON map構造とnode metadataを含む保守的なRAM見積りとする。appendで再利用したArcの本文は一回だけ数える。0は保持cache無効で、要求処理を拒否しない。entry自体が枠を超える場合も非cacheの作業領域として要求を組み立てる。

要求snapshotは変換結果をleaseでpinする。LRUから外しても使用中のArcを解放済みと数えず、retained/live/pinned byteを区別する。leaseのcloneは同じpin集合を共有する。lease用Vec<Arc>とHTTP request用のowned JSONは要求作業領域であり、Frameのlive/pinned byteとは区別する。HTTP完了/失敗/取消し後にleaseを解放し、背景shell collectorへ送信履歴のleaseを渡し続けない。HTTP request用のowned JSON構築は一時領域であり、保持cacheの予算とは分ける。

予算の照合で、従来 `history_bytes` がAGENTS LRUとUI metadataにもそれぞれ独立適用されていた不一致を修正する。history_bytesは本ReplayCache専用とする。UIのnode metadataは本文とbody_bytesに合算し、表示anchor周辺の3nodeは従来どおり作業領域として区別する。AGENTSの保持LRUは廃止するが、Turnのimmutable instruction_snapshotと同Turn retryのDB版再利用、driver内のそのTurnのArcは維持する。この是正はroot担当のui/instructions変更と組み合わせる。

DB transactionが失敗したcacheの一時entryに依存してHTTPを開始しない。次回利用時にも元経路metadataを照合するため、rollback前の新経路をcacheが権威として復活させることはない。cacheは再起動へ永続化しない。

## 境界の検証

`tests/replay_cache.rs` は7件で、通常appendの変換件数、共有LRUとpin clone、0/過大entry、経路置換/巻戻し/版変更、effort-only再利用、model epoch、rollback後の再照合を確認する。実driverのA→B→Aと原文保持は `tests/runtime_features.rs` が別に担当する。

失敗HTTPのlease解除位置も確認した。初期接続では成功応答の分岐後だけ解除しており、context超過から要約待ちへ入る間に旧要求の13,156byteがpinされた。既存のoverflow結合試験に、summary HTTPが保留中のpinned_bytes=0を追加すると失敗した。解除をHTTP outcome取得直後（成功/失敗/取消しの分岐前）へ移し、同target13件と全targets Clippyの成功を確認した。要約を待つために終了済み要求のpinを保持しない。

完了Turnしかない背景RunのIdleでは前Turnのinstruction Arcも解放する。再開に必要な指示はDBのTurn snapshotから取得でき、ファイルを同Turn retryで再観測する規則には変えない。cache導入後の実Runを反復する資源計測では、retained予算内とHTTP pin解放を別に確認する。

RAM見積りは保持entryの文字列/Arc配列に加え、HashMapのusable capacityからspare bucketsとcontrol領域も含めたslot数、VecDequeのcapacityを数える。LRUで疎になったcontainerはshrinkし、空なら新しい空containerに置換する。多数の小Threadから少数の大entryへ移った時、使っていない旧bufferを0byte扱いで残さない。通常hitごとのrehashは行わない。FrameのArc headerとJSON Valueの所有文字列/配列capacity、map構造を含めるが、allocator/OS RSSの厳密な同一値を主張するものではない。

`Control::replay_cache_stats()` は既存attachment cache_statsと同種のpureな観測用getterで、新CLI/wire操作ではない。Frame retained/live/pinnedとmetadata、hit/append/rebuild/変換node数を返す。実HTTP完了後にcollectorへpinが残らないことはlifecycle試験へ追加する。Runが背景だけでIdleへ入る時は前Turnのinstruction_body Arcも解放し、次に必要ならimmutable DB snapshotから取得する。

`tests/replay_cache.rs` は正常append時に新nodeだけをparseすること、同じ経路のhit、全Thread共通LRUとeviction後再取得、evict中のrequest pinとlease clone、0/過大entryの非cache処理、effort-onlyの再利用、置換/巻戻し/本文版変更、A→B→Aでの旧opaque非復活、実forkの別entry、API項目とDB原文の不変、多数Threadから空へのcontainer回収を対象とする。

## 暗号化本文のない推論項目（M8）

同epochのreasoning itemは、encrypted_contentの有無だけで削除しない。store:falseに対してIDのみ／summaryを持つ項目が拒否される可能性はprovider依存の仮説として扱う。特定の接続先での過去の比較では、この拒否は再現しなかった。接続先やモデルを変えた際は、元itemとencrypted_contentを除いたitemの再送を対照して確認する。過去の非再現を全providerの互換保証にはしない。

[OpenAI公式reasoning guide](https://developers.openai.com/api/docs/guides/reasoning#preserve-reasoning-without-stored-responses)はstatelessで返された推論項目の保持・再送を案内しているが、個別proxyの変換や欠落項目の受理を保証するものではない。現在のepoch境界、元ID/summary/暗号化本文の無変更保持、モデル／profile変更時の旧項目除外を維持する。欠けた暗号化本文を作らず、summaryを暗号化本文や通常回答へ変換しない。新しいprovider設定・自動fallback・Core stateは追加しない。

比較結果をすべてのproviderの互換性証明とは扱わない。実際に返された同epoch項目の再送が拒否される接続先を追加する際に、そのadapterの入力契約を確認し、元の監査本文を保持したまま処置を再検討する。実proxy試験の範囲は proxy検証（非同梱の検証記録） に記録する。
